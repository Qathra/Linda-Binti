1. Sign in

Email and password

Register, login, and device session. The Access Code and the SOS code are never sent or stored on the server.

bcrypt hash

The password is stored only as a bcrypt hash. Login checks the hash. The plain password is not kept.

Rate limit

Register, login, and refresh are rate-limited so repeated attempts are rejected.

↓

2. Session tokens

Access JWT

Short-lived bearer token. Every protected endpoint checks this token before a role is allowed.

Refresh token

Stored in SQLite. Used to continue a session. Rotated on refresh. Revoked on logout and on password change.

↓

3. Role check after the token is valid

USER

Survivor cloud account

  • Own reports only
  • User-level AI: report analysis and assistant chat
  • Submit anonymised analytics events
Cannot open another person’s reports, the NGO dashboard, the staff list, or the audit log.

NGO_STAFF

Authorised monitoring

  • Dashboard, case counts, trends, and statuses
  • Aggregate analytics and AI urgency flags
  • Update case status
No raw survivor report text. No staff management. No audit log.

NGO_ADMIN

Staff, audit, and monitoring

  • Everything NGO staff can view
  • Create and list staff accounts
  • Read the audit log
  • Edit education content
Still no raw survivor report bodies.

Privacy boundary

NGO staff and administrators see aggregates, flags, and case status. They do not receive private report text, phone numbers, the Access Code, or the SOS code. Very small analytic groups stay suppressed. A USSD gateway must present its key; the caller’s raw number is not stored.
